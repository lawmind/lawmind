# 3. OPERATING RULES — v7.2

## 3.1 Shared worktree

- atomic `HEAVY_BOX`, `GIT_COMMIT`, `MIGRATION_SLOT`;
- exact owned staging only;
- never `git add .`, `git add -A`, or `git commit -a`;
- no reset/rebase/stash/checkout over another lane's work;
- re-anchor HEAD/status/leases immediately before staging;
- if HEAD moved, inspect intervening commits before commit;
- do not stop a healthy worker for Git convenience;
- avoid shared `CURRENT_PLAN.md` mutation during parallel rounds.

## 3.2 Evidence

Every number comes from an executed command/query or is explicitly labelled received/last-observed.

`UNKNOWN` stays `UNKNOWN`.

A successful process exit is not proof that intended durable output exists.

A failed observation is not evidence of absence.

## 3.3 Three-attempt stop

Three materially equivalent failed attempts at one issue:

- STOP;
- publish actual outputs;
- best current hypothesis;
- tie-break evidence needed.

No fourth blind attempt.

The known Windows reserved-name `NUL` pseudo-entry has already hit this stop. Do not keep attempting cleanup in unrelated rounds.

## 3.4 Inter-wave integration seal — NEW P0 RULE

After every concurrent **mutation** wave, and before the next mutation wave:

1. list every expected completed commit;
2. prove each is `ANCESTOR_OF_HEAD`, `HEAD`, `SUPERSEDED_BY_<commit>`, or `NOT_IN_HEAD`;
3. `NOT_IN_HEAD` for completed required work = STOP;
4. inventory staged/tracked/untracked product dirt;
5. read `GIT_COMMIT`, `MIGRATION_SLOT`, `HEAVY_BOX`;
6. verify current authority-file hashes;
7. process explicit unacknowledged P0/CCR/HANDOFF/ACTION_REQUIRED bus items addressed to the next active lanes;
8. never auto-cherry-pick missing work;
9. publish seal receipt.

The seal is mechanical and may be run by LCC/coordination. It is not a substitute for FIFTH at formal gates.

## 3.5 Critical bus ACK protocol — NEW

New actionable bus messages should include:

```
kind: INFO | HANDOFF | CCR | ACTION_REQUIRED | BLOCKER | GATE_EVIDENCE
severity: INFO | P2 | P1 | P0
requiresAck: true | false
blockingGate: <gate|null>
supersedes: <seq|null>
```

Acknowledgement is append-only:

```
ackOf: <seq>
status: ACKED | DEFERRED | SUPERSEDED | BLOCKED
disposition: <short exact reason>
```

Do not infer urgency from message age alone.

Before an ACTIVE lane mutates, unresolved `requiresAck=true` messages addressed to that lane are triaged.

Legacy messages without metadata are not rewritten; a one-time actionability sweep may classify subjects/explicit fields only.

# 6. WRITE RELIABILITY — R16 IDEMPOTENCY BASELINE

## 6.1 Contract

`Idempotency-Key` is a LawMind API convention, not claimed as a ratified HTTP standard.

Scope:

```
authenticated principal
+ HTTP method
+ canonical route template
+ idempotency key
```

Request fingerprint includes:

- validated body;
- path parameters;
- operation-significant query.

Semantics:

- same key + same fingerprint → same logical mutation/result;
- same key + different fingerprint → `409 IDEMPOTENCY_KEY_REUSE_MISMATCH`;
- concurrent same key → one logical executor; follower waits/replays or receives contract-approved retryable in-progress response;
- omitted key → legacy behavior during compatibility window.

Never dedupe by annotation text, paragraph, date, matter content, or semantic similarity.

## 6.2 Preferred persistence architecture

Prefer one generic user/matter-DB idempotency ledger over six independent nullable domain columns, unless committed implementation evidence proves the generic design unsafe.

Conceptual identity:

```
(principal_id, method, canonical_route, idempotency_key)
```

Store enough deterministic state to validate fingerprint and replay the logical result.

The domain mutation and successful idempotency receipt must be transactionally coupled. A crash/lost response after durable mutation must not create a second logical mutation on retry.

Do not invent ledger pruning/retention policy in implementation. Measure growth and route privacy/erasure implications through the existing policy process.

## 6.3 Current-v1 required endpoints

Token required:

- annotations;
- matter creation;
- matter events;
- data requests;
- verification confirmations;
- training consent.

Already naturally idempotent:

- matter authority add;

# 7. CONTROL PLANE AND LONG-RUN HEALTH

## 7.1 Durable-progress health

Known Windows constraint:

- scheduled-task descendants may expose empty `Win32_Process.CommandLine`;
- wrapper PID exit/reuse is therefore not proof of logical-worker death.

Health order:

1. declared durable output;
2. declared receipts/log freshness;
3. current process evidence if available;
4. resource lease as takeover veto.

States should distinguish:

- `RUNNING_BY_PROGRESS`;
- `RUNNING_PROCESS_CONFIRMED`;
- `STALE_REGISTRATION`;
- `STALLED`;
- `FAILED_CONFIRMED`;
- `UNKNOWN`.

`UNKNOWN` is never restart-safe.

## 7.2 Restart unanimity

Never recommend restart/takeover unless all required evidence agrees:

- durable progress stale beyond documented bound;
- receipts/logs stale;
- no valid current process descendant;
- no healthy-by-progress resource lease.

An absent wrapper PID alone cannot kill NEW1.
